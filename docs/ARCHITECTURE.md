# Integrated Recorder Architecture

[English README](../README.en.md) | [한국어 README](../README.md)

This document describes the current implementation. Reserved protocol shapes and future ideas are called out as such; they are not claims of implemented features.

## Core invariant

The canonical archive is the source media received from the broadcaster plus metadata needed to reconstruct its timeline. Acquisition does not decode, encode, transcode, or remux media. Core has no platform domain model: resource types, field keys, adapter state, and interaction data remain opaque strings or JSON values. Platform-specific discovery stays in an external adapter process. Core alone owns archive identity, `recording.json`, metadata timelines, track/segment identities and ordinals, manifest snapshots, gap and integrity semantics, canonical publication ordering, recording-owner fencing, ingest admission, retry policy, and logical archive keys. A storage provider handles only physical placement and transport for complete objects.

## Runtime generations and package boundaries

```text
Browser ── stable HTTP listener ── Runtime Host
                                      ├─ Control generation(s)
                                      │    ├─ API/UI, auth, Watches, settings, management projections
                                      │    ├─ preview, integrity, export, retention coordination
                                      │    └─ generation-pinned Engine IPC clients
                                      ├─ Recorder Engine generation(s)
                                      │    ├─ acquire.Manager, HLS scheduler, metadata monitor
                                      │    ├─ Core archive model, commit ordering, and owner fence
                                      │    ├─ adapterhost ── Adapter Protocol ── source adapters
                                      │    └─ PhysicalObjectStore ── Storage Protocol ── pinned provider
                                      ├─ immutable adapter and storage-provider catalogs
                                      └─ shared ingest/resource coordinator
```

The production container starts `runtime-host` as PID 1. It owns the stable public listener, release verification/installation, generation supervision, routing, leases, draining, rollback, and the process-shared resource coordinator. It does not parse HLS or recording manifests and does not interpret platform metadata. `control-plane` is replaceable: it owns management APIs and Watch scheduling, but not canonical media acquisition. Each `recorder-engine` process owns its own `acquire.Manager` and any work it admitted. Replacing or killing a Control process does not signal its Engine. A Recording normally remains on its starting Engine, but an eligible same-adapter-set Recording can be transferred to a new Engine through the Host handover path.

```text
candidate verified and ready
  → fence old Control admission and drain accepted mutations
  → atomically switch active Control epoch and stable route
  → enable candidate background work
  → attempt eligible per-Recording handovers to the new Engine
  → keep old Engine generations while remaining leases still reference them
  → drain, detach, stop, and collect an old Engine only after inventory is empty
```

Application release activation keeps already-running Engine processes alive while a target Engine is prepared. During normal Host operation, the target uses the Recording's exact pinned adapter and storage-provider sets, restores its resource/current-media context, performs adapter refresh when the current media needs it, fetches a fresh HLS manifest, and stages the next uncommitted media payload in bounded ingest memory. It makes no canonical archive writes before ownership transfers. The source continues during speculative preparation, then stops new manifest admission and drains accepted writes; the target repeats readiness against the final canonical root before the owner CAS. Any pre-transfer failure leaves the source owner in place. Protocol v1 does not preserve the original resolve workflow input, so the target does not fabricate a new resolve/continue request; existing resource/media context plus the pinned adapter's refresh contract is the supported continuation path. Handover is allowed only when both immutable adapter-set and storage-provider-set identities match; neither source-adapter nor storage-provider behavior is upgraded during a live Recording.

The Host-owned durable `recordingowner.Store` tuple (Recording, Engine generation, worker instance, monotonic epoch) is the canonical write authority; the generation registry lease is only a retirement projection. Every canonical mutation checks that tuple under a cross-process per-Recording lock held through the full commit. On cold Host startup the selected active Engine installs the fence before mutating `LoadAll` recovery: it locks owner shards, durably fences every prior active owner while preserving each epoch high-water mark, then marks active archives `interrupted`. Once that Engine is ready, the Host atomically clears the stale lease projection and marks unattached draining generations dormant before it enables Control/API work. This is an explicit fail-stop recovery policy: a Host crash does not resume active Recordings, but any orphan Engine remains unable to commit, and the canonical payloads, sidecars, root, and metadata timeline already committed remain intact. Recovery is idempotent, so no per-handover journal is needed for this policy; the durable owner file determines the pre/post-CAS epoch and every cold start converges active recordings to the same interrupted state. Replacing the Runtime Host, container image, operating system, or bundled FFmpeg remains a separate maintenance operation and is not covered by application-generation zero-downtime behavior. See `docs/ACTIVE_RECORDING_ENGINE_HANDOVER.md` for the ownership and crash matrix details.

Host-owned `/data/runtime/state/generations.json` records generation lifecycle and recording-to-Engine leases. The Host reconciles leases against bounded inventories from every ready Engine before retiring a generation. The previous known-good release remains protected as a rollback target. Release directories are immutable and separate from canonical `recordings/` data. Remote artifacts are accepted only after a detached Ed25519 signature and manifest-declared size/SHA-256 checks; GitHub is a discovery/download source, not a trust root. Compatibility is checked against explicit runtime, IPC, archive, and management-schema declarations rather than inferred from SemVer.

The Host resource coordinator keeps the existing ingest limits global while Engine generations overlap: RAM reservation, per-recording limits, pending object/byte admission, and the single canonical writer permit are shared over authenticated local IPC. The storage facade reports its own bounded read/write throughput, latency, error, queue, buffer, and writer metrics; remote capacity is explicitly unknown rather than shown as unlimited. Integrity, preview, export, and Watch worker pools remain Control-generation services; the old Control fences and drains accepted jobs before shutdown, and the candidate takes over after activation. Storage v1 selects one canonical primary backend for the installation; it does not provide per-recording/multi-pool placement, replication, tiering, or automatic archive migration.

Control and Engine communicate with bounded, authenticated local IPC using versioned JSON frames, request IDs, deadlines, generation/instance identity, and a fixed maximum frame size. The public listener is never bound by an application child. The Host routes new requests to the active Control and waits for routed in-flight requests during handoff. A brief mutation fence can return a retryable unavailable response while the candidate application opens shared management state; the listener itself remains bound.

The Runtime Host recognizes three plugin admission provenances: `bundled`, `registry`, and `operator`. Provenance records how the exact executable bytes were admitted; publisher affiliation (`first_party`, `third_party`, or `unknown`) is separate. The Host, never the executable descriptor, assigns provenance and publisher. Bundled inventory is an explicit Host declaration: production bundles `source.hls` and `storage.local`; `/external-adapters` contains operator-supplied binaries and is considered only when `IR_ALLOW_OPERATOR_PLUGINS=1`. `/adapters` is not scanned as an arbitrary executable directory. Registry v1/v2 remain supported; Registry v3 can carry publisher metadata. Only the exact canonical HTTPS v3 catalog URL `https://integrated-recorder.github.io/plugin-registry/catalog-v3.json` is recognized as the official Registry authority. A custom Registry remains operator-controlled even if its document claims `first_party`. Registry approval identifies exact bytes and distribution metadata; it does not claim the code is safe. The Registry currently operates in solo-maintainer mode: changes still require a PR and successful required CI/artifact validation, while independent approving reviews are not required. The compatibility API field `reviewed` indicates authoritative admission, not independent human review. All plugins are native executables and are not sandboxed.

Artifacts identify exact bytes by SHA-256, while Host-assigned trust attestations are stored separately in immutable adapter/storage sets. The attestation participates in set identity, so identical bytes admitted as operator and later by the Registry produce distinct sets and generations. There is no automatic trust promotion based on digest equality. Legacy sets without an attestation remain readable as `legacy_unclassified` and are treated conservatively; their manifests are not rewritten. Bundled IDs `hls` and `local` are reserved against Registry/operator replacement. Generation identity remains `(application release, adapter set, storage provider set)`, and recordings keep their originally pinned generation.

The Runtime Host treats configured operator adapter directories as import sources, never as executable paths for application generations. When operator plugins are enabled it periodically snapshots stable regular executable files named `integrated-recorder-adapter-*`, probes their Protocol v1 descriptors, hashes them, and publishes content-addressed immutable artifacts and immutable adapter-set manifests under `/data/runtime/adapters`. A generation's application identity is the tuple `(application release, adapter set, storage provider set)`: changing either set creates a different generation even when the application release is unchanged, while an application update carries forward both currently selected sets. Adapter reconciliation, storage-provider lifecycle operations, and application updates share the Host operation gate, so one generation cannot combine parts of competing candidates. Control and Engine receive only their generation's private immutable adapter-set `bin` directory as `ADAPTER_DIR`. A changed, added, or removed adapter therefore stages and activates a new application generation through the ordinary readiness/fencing path without restarting the Host or container. A Recording is eligible for Engine handover only when the target uses the exact same adapter-set and storage-provider-set identities; set changes alone do not migrate existing recordings. In the live-Host handover path, old adapter artifacts remain pinned until the Recording owner and generation references move and drain. `POST /api/runtime/adapters/reconcile` requests an authenticated immediate scan; automatic reconciliation also runs periodically. Invalid candidates are excluded by a bounded, Host-process-local quarantine keyed by content digest; the same digest is skipped while cached, but can be probed again after a Host restart or cache eviction. An invalid replacement retains the prior artifact with the same binary name. Valid independent candidates can still activate. Fatal source inventory or catalog-storage errors leave the active set unchanged. Referenced artifacts are retained for active, draining, staged, rollback, lease, and Engine roots; collection fails closed when runtime references cannot be reconciled safely.

When `IR_PLUGIN_REGISTRY_URL` is configured, Runtime Host can import curated remote executable plugins.

## Storage provider process and generation pinning

There is no special production local-storage path. `storage.local` is a standalone bundled Storage Provider Protocol v1 executable, plugin ID `local`, and the first reference storage implementation. Fresh and migrated installations use it as the default primary provider even when no Plugin Registry is configured. Core's `storage.Store` facade and `ObjectStoreArchiveBackend` own archive semantics. Their `PhysicalObjectStore` boundary accepts only validated logical keys and byte streams; a provider cannot create a Recording or decide its metadata, segment ordinals, gap state, ownership, retry policy, or canonical commit order. Every production generation, including local-primary generations, names an immutable storage-provider set. The application process starts the exact executable/configuration snapshot named by that generation and communicates over an authenticated private Unix socket. Control frames and configuration are bounded JSON; object bodies use streaming HTTP-style requests over the socket, raw bytes rather than base64, exact content lengths, cancellation, and backpressure. Core stages one object under private runtime staging, computes expected size and SHA-256, then streams it to the provider without making an additional whole-object RAM copy. Recording writes, playback, integrity reads, deletion, and cold recovery use this provider path; there is no local-only syscall bypass in the production archive path.

Runtime Host imports the bundled `storage.local` executable through the same descriptor probe, content-addressed artifact catalog, immutable provider-set construction, readiness probe, and generation pinning used for other providers. It supplies a fixed private root at the existing `<DATA_DIR>/recordings`; public provider configuration cannot select an arbitrary host path. This preserves the established archive layout without copying or rewriting recording bytes. Logical `recordings/<id>/...` objects retain their existing physical location under that root. Other logical object namespaces use a provider-private physical subnamespace, so implementation metadata does not collide with legacy recordings or become a Core runtime directory. Runtime state remains Core-owned under `/data/runtime` (including generations, owners, operation state, adapter/storage catalogs, Plugin Registry desired state, updates, secrets, IPC files, and recovery coordination); the provider is given no `/data` root.

On startup the Host resolves/imports the bundled executable, selects or adopts the local provider set for legacy empty-set generations, launches and probes the exact pinned provider, and only then opens the archive for load/recovery and generation readiness. The one-time legacy adoption changes Host-owned provider identity state only: existing `/data/recordings` bytes and archive documents are not migrated or rewritten. A missing, corrupt, or unavailable selected provider is an explicit degraded/fail-closed condition. Production never falls back to `LocalFilesystemBackend` or direct filesystem I/O. `storage.local` is bundled and mandatory, is always available independently of Registry connectivity, and cannot be uninstalled through the plugin API. Its root is Host-managed rather than a user-editable provider configuration field.

Protocol v1 requires `object.read`, `object.write`, `object.stat`, `object.list`, `object.delete`, `object.range_read`, and `atomic_replace`. A successful `Put` means one complete object was published. On failure/crash the old complete object or new complete object may be visible, never a partial canonical object. If the transport response is ambiguous, Core checks the stored size and bytes/hash before accepting the commit or allowing its normal retry path. Core remains the retry/backoff authority; providers may use only bounded transport retries. Protocol and conformance details are in `docs/STORAGE_PROVIDER_PROTOCOL_V1.md` and `cmd/storage-provider-conformance`.

Runtime Host imports bundled and Registry-approved provider executables into the private `/data/runtime/storage-providers/artifacts/<sha256>` catalog and stores immutable configured provider sets under `.../sets/<set-id>`. Registry-approved files are exact-size/SHA-256 checked and then descriptor-probed for provider ID, version, protocol, schema, and capabilities. The bundled `local` artifact is imported from the Host's configured bundled executable source and verified through the same Protocol v1 probe; it does not require a Registry entry. Config values and secrets are written only to the set's private `0600` configuration snapshot; secret values are not returned by APIs and are sent to the provider over authenticated local IPC. The local root is Host-supplied and cannot be overridden through provider configuration. Provider processes receive an empty environment and are trusted native code under the same OS account, not sandboxed. Storage provider configuration secrets are permission-restricted but are not encrypted at rest.

`GET /api/runtime/storage/provider` reports the primary backend and installed providers without exposing local paths, artifact digests, IPC credentials, endpoints, or secrets. The local provider is projected as a bundled, installed, active-capable plugin and cannot be uninstalled; its fixed root is not a public setting. `/api/runtime/plugins` supports typed Registry browsing and install/update/uninstall for Registry providers; installing verifies and stores an executable but does not activate it. `/api/runtime/storage/providers/{id}/config` configures Registry providers, `/probe` starts the exact configured set, validates its configuration, then has Core exercise put/stat/list/read/range/delete/missing-object behavior in a reserved private namespace. `/activate` stages a ready application generation that pins that provider set. The Storage page separates these actions. Storage backend selection is protected by the same Host operation gate as app/source-plugin updates. Provider-version updates produce a new generation; active recordings remain on their original Engine and provider artifact, and old artifact sets stay rooted while their generation/recording references remain.

Storage v1 has exactly one primary backend per installation. Changing the physical backend kind is rejected while recording-generation leases exist and unless the active and target archive namespaces are proven empty. No backend switch implicitly migrates archive data. A selected provider that cannot start or probe causes generation readiness to fail; the Host does not silently create a local archive or invoke a direct-local fallback. Storage-provider set identity is part of the Engine handover eligibility check, so a Recording is not transferred across provider sets. The provider protocol and backend-neutral VOD segment route support a single byte range and stream only the requested range from the selected provider.

- `internal/adapterproto` defines language-neutral Protocol v1 envelopes, descriptor/schema validation, resources, workflows, media sources, refresh policy, adapter-owned state, and optional Watch check messages.
- `internal/adapterhost` consumes only the immutable adapter-set directory assigned to its application generation by Runtime Host, supervises long-lived processes, validates descriptors/resources, resolves settings, and manages workflow sessions inside the owning application process.
- `internal/watch` stores durable management state, runs bounded polling, deduplicates sessions, and starts/reconciles automatic Recordings.
- `internal/pluginconfig` stores user configuration/secrets separately from adapter-owned opaque state/state secrets. Interfaces are backend-neutral; the current implementation uses files.
- `internal/interaction` bounds and expires generic interaction progress messages.
- `cmd/adapters/hls` and `internal/adapters/hls` build the bundled generic HLS source bridge. Owncast source behavior is maintained separately in `integrated-recorder/source.owncast` and is intended for Registry distribution, not bundling.
- `internal/hls` parses the supported HLS subset. `internal/acquire` (owned by `recorder-engine`) owns polling, refresh, retries, segment acquisition, sequence epochs, metadata observation, and recording lifecycle.
- `internal/network` validates public destinations and pins each connection to a freshly validated address.
- `internal/domain` holds archive-owned types independent of adapter wire types. `internal/storage` owns archive formats and canonical commit semantics; its `PhysicalObjectStore` boundary handles external object placement. `internal/storageproto` implements the separate streaming Storage Provider Protocol; `internal/storageprocess` supervises provider executables; `internal/runtimehost/storagecatalog` owns imported artifacts and immutable configuration sets. `internal/server` exposes the API and static management page inside a Control generation.
- `cmd/storage-local` and `internal/storagelocal` implement the bundled `storage.local` reference executable. It maps logical keys to physical files under the Host-provided archive root and does not import or interpret Core Recording types.

## Adapter process and protocol

Adapters are standalone executables. Runtime Host starts bundled adapters only from the exact paths in its Host-owned inventory. It scans `/external-adapters` as operator sources only when `IR_ALLOW_OPERATOR_PLUGINS=1`; Registry artifacts enter through the Registry verifier and immutable catalog, not by scanning `/adapters`. All admitted binaries use the same Protocol v1 discovery and immutable generation pinning. Control and Engine do not scan mutable source directories.

IPC is bounded newline-delimited JSON. V1 keeps its original untyped request/response wire form; request IDs, protocol version, method, result, and structured errors are validated. The parser also distinguishes typed frames and the reserved `notification` shape, but asynchronous notifications are not delivered by the runtime. A notification received where a response is expected is a protocol error.

The host serializes calls to each process. Timeout, cancellation after a request is written, malformed/oversized output, unexpected EOF, request-ID mismatch, protocol mismatch, or process exit makes that process unusable. The next operation may restart it lazily after bounded backoff. Every restart performs `describe`; adapter ID, version, protocol version, and the canonical descriptor fingerprint must match the original discovery descriptor. There is no background restart loop. Shutdown sends the generic shutdown request and then terminates the child within a bounded period.

V1 implements `describe`, legacy `resolve`, `resolve.begin`, `resolve.continue`, `refresh`, and `shutdown` where the descriptor advertises the relevant generic capability. Adapters declaring `watch` may answer `watch.check` with `offline` or `live`; network or malformed-response errors are not offline observations. A result may include media for the existing `StartResolved` path; otherwise Core may use one interaction-free stateless `resolve`. This optional extension keeps protocol version 1 and leaves old adapters unchanged. Other operation names remain reserved or return a structured unsupported error. Unknown optional capability strings with valid syntax are retained and ignored by older Core versions; protocol-version mismatch remains fatal.

Descriptors may include optional `branding.icon` presentation metadata. The current format accepts only `image/png`: its base64 JSON payload is limited to 64 KiB, each dimension is at most 512 pixels, and the complete image must decode as PNG. SVG and external URLs are rejected. Branding does not change adapter semantics and is excluded from the descriptor fingerprint. Adapter API views expose an authenticated `/api/adapters/{id}/icon` URL instead of repeating image bytes in polled list responses.

Owncast is first-party software, but it is not bundled software. Its separate source repository and Registry release are subject to their own source and asset licensing.

## Resources, configuration, and workflows

An adapter descriptor declares opaque resource types and allowed parent-type edges. Core validates each resource reference and every edge against that declaration for API hints, config scopes, workflow discoveries, and persistence targets. Core does not interpret the type names. The active chain is bounded in depth and cannot contain a cycle.

Configuration has distinct stored and effective views. Effective values are composed from plugin scope, parent-most resource, each child, and the current resource; more-specific values override less-specific ones. A field's `inherit` flag controls whether ancestor values or secrets flow downward. It defaults to `false` for every control. `clear_values` removes an override and returns that key to inherited/default behavior; `clear_secrets` explicitly removes a secret. Empty ordinary values are values, while a blank secret submission leaves the stored secret unchanged.

`resolve.begin` accepts adapter-defined input before a stable resource is known. The adapter may return a resource, after which Core validates its chain and loads matching effective configuration, secrets, and adapter state before continuing. Challenges use the same validated schema vocabulary and generic workflow state. Each challenge field can declare persistence as `forbidden`, `optional`, or `required`, plus a `plugin`, `current_resource`, or explicit `resource` target. Explicit resource targets must be members of the validated chain. Persistent challenge fields must also be declared in the target scope's descriptor schema with the same control; runtime-only fields are ephemeral. This prevents a saved value from becoming invisible to later resolutions.

Workflow sessions are process-local and bound to the adapter process generation that created them. A process restart expires a stale workflow deterministically instead of forwarding its ID to a fresh process. Sessions have a 30-minute idle TTL, a 128-session bound, and a 32-transition cumulative limit. `DELETE /api/resolve-workflows/{id}` cancels a session. Expiration/cancellation removes its title and interaction progress. Workflow sessions do not survive a Core restart.

The browser uses one schema renderer for recording input, settings, and challenges. It handles the declared `visible_when` grammar (`field` with `equals`, `not_equals`, or boolean `truthy`, recursively combined by `all`/`any`), defaults, select/multi-select values, inherited sources, and explicit clear operations. Secrets are never read back as plaintext. Prompt/display/status data is rendered as text; navigation accepts only HTTP(S) URLs and opens with `noopener noreferrer`. Adapter HTML and scripts are never executed.

## Adapter-owned state and refresh

Adapter-owned opaque state is separate from user configuration. State values and state secrets are stored under adapter and optional resource scopes; Core does not interpret their keys. Mutations are accepted only for scopes in the current validated chain. State is supplied to later resolve/refresh calls and persists across adapter process restarts. It is not included in recording metadata or public API responses.

The default file state-secret backend is separate from ordinary state and uses restricted permissions, but provides **no at-rest encryption**. The user secret backend has the same plaintext-at-rest limitation. Both are backend-neutral so a later encrypted or OS-backed implementation can replace them. Neither should be described as an encrypted vault.

An adapter with the refresh capability may declare an expiry time, refresh lead time, and HTTP status codes that should trigger refresh. Core does not infer token expiry from status codes. It performs proactive refresh and adapter-declared status refresh; adapter code supplies the replacement media source. Core validates its media/request policy and public manifest URL before committing staged adapter-state changes and swapping the active URL, headers, forwarding policy, and refresh policy. A failed validation/refresh does not replace the active source. Refresh errors exposed outside Core are generic and omit signed URLs and adapter secrets.

## Media acquisition and HLS support

The adapter resolves input into a generic media source. Core owns playlist parsing, rendition selection, request/header policy, retries, exact segment-byte storage, SHA-256, gap detection, and VOD generation. Adapter-supplied headers default to same-origin forwarding. An adapter may declare an exact origin allowlist; Core reapplies that decision on each request/redirect and independently enforces SSRF/public-address validation.

The current HLS subset handles a single self-contained rendition, MPEG-TS or fMP4 media objects, init maps, byte ranges with explicit safe range arithmetic, discontinuities, program date/time, and completed `EXTINF` segments. It can ignore LL-HLS partial tags when the same playlist contains complete segments. It explicitly rejects encrypted HLS, external audio/video/subtitle renditions, I-frame-only playlists, URI variable substitution (`EXT-X-DEFINE`), delta (`EXT-X-SKIP`) playlists, and partial-only LL-HLS. DASH, subtitles as separate renditions, and DRM/key acquisition are not implemented. Rejections are deterministic; source media bytes are not rewritten.

Media sequence numbers are source coordinates, not archive identity. Core keeps `ArchiveOrdinal` as an append-only identity for archive/preview references, while a separate `TimelineOrdinal` is a revisionable playback position. Source epochs and discontinuity sequence are part of the coordinate so a reset or reused media sequence does not collide with an earlier object. VOD reads use the current timeline projection rather than treating discovery order as playback order.

## Repairable archive inventory

`internal/archiveindex` defines a bounded, transport-independent inventory over the canonical recording, persisted as a versioned `archive-index` sidecar with a strict serialized-size limit. The recording ID identifies one Core capture execution; a separate opaque source-session identity represents the broadcast/resource session when the adapter supplied enough evidence. Core hashes the resource and optional adapter `session_ref`; it does not expose those raw identity inputs as the inventory identity. If no explicit session reference exists, the identity remains scoped to that recording rather than assuming that a resource/channel is one broadcast.

A logical media identity is derived from source coordinates—session, track, source epoch, discontinuity sequence, media sequence, and object kind—not from when Core discovered it or which archive ordinal it received. Each coordinate can hold bounded claims from live origin, historical acquisition, peer, or import sources. Claims retain their own provenance, payload path, exact size, SHA-256, verification result, and evidence. Repeating the same bytes is an idempotent duplicate claim. Different bytes for an already claimed coordinate are recorded as a conflict; Core keeps the previously selected verified payload and never overwrites it. Coverage distinguishes `unknown`, `known_missing`, `acquisition_failed`, `present`, and `conflict`; an observation that bytes are present or conflicting takes precedence over an older missing/failure interval.

The inventory's playback timeline is a revisioned projection. Core can insert a late prefix or fill a middle gap without renumbering `ArchiveOrdinal` or rewriting stored media. It assigns compact `TimelineOrdinal` values to selected media objects in deterministic coordinate order and rebuilds the VOD playlist/index from the current projection. Duration and seek positions therefore follow newly available segment durations; missing time is not invented when its duration is unknown. Existing frame assets remain identified by append-only archive ordinal while their projected playback times are recalculated.

Capture lifecycle and archive lifecycle are separate. Stopping or interrupting capture closes live admission, but leaves the archive repairable. Only an explicit seal ends repairability. Core owns an automatic recovery scheduler: it starts historical work after the first live manifest, rechecks declared gaps and failures, and continues bounded work after capture ends. One historical worker serves each Engine process. Each pass has a 128-unit source-driven work budget shared by media coordinates, new `known_missing` coverage publications, and required init-object acquisitions; this is a fairness/checkpoint quantum, not a request-concurrency limit. A media coordinate reserves one unit for acquisition and any resulting failure publication; an absent init object reserves one additional unit before either request starts. Existing `known_missing` gaps cost no new unit and remain eligible for slow recheck. Exhausted passes report continuation and return the Recording to the FIFO tail. Immediate events coalesce into the existing queue slot and promote delayed work; events received during a pass force one immediate reconciliation without charging the delayed retry/recheck counter. Retryable failures use capped exponential backoff. No-progress declarations use slow, finite rechecks. A single queue slot per Recording, bounded queue capacity, and overflow rescan preserve fairness without spawning unbounded work.

Historical media network fetches use a bounded per-Manager window: concurrency starts at two and can grow to four after sustained healthy ingest pressure. A window writes response bytes to private temporary files, checks the byte limit, declared size, and SHA-256, then materializes and commits one result at a time in manifest order through the existing canonical writer and owner/epoch fence. The scratch slot count is bounded by the configured ingest global-byte and maximum-payload ratio, capped at four; separate Managers do not share a Host-wide scratch-disk quota. The Manager-local governor observes ingest buffer reservations, queue depth/bytes/age, and writer utilization. Ordinary requests bypass historical admission and signal live activity; while their response bodies are in flight, the governor stops admitting new historical fetches. Existing historical requests are allowed to finish. Ingest pressure reduces historical concurrency to one or pauses new admissions, while sustained healthy pressure can raise it gradually. This is an admission and concurrency bias, not a byte-rate bandwidth guarantee: Core has no reliable live-lag or per-priority WAN-throughput measurement, and the governor is not shared across Managers. Live acquisition remains on its separate worker pool and is not blocked by a historical network wait.

Restart rebuilds work from the archive inventory and private acquisition context; volatile timers are not required. Recovery stops for a sealed archive or when no bounded candidate remains. Terminal owner release uses the exact lease ID and retries transient failures with bounded backoff without repeating archive acquisition. Unresolved releases remain observable and are surfaced by ingest shutdown after bounded final attempts. Canonical commits still serialize through the common per-recording owner/epoch fence. A stale Engine cannot publish a claim or playback projection after losing that fence. Handover drains in-flight historical work before it snapshots the source, then keeps the source recovery worker parked until resume or retirement. Inventory read-modify-write and root/timeline updates use the same fenced canonical mutation path. The Runtime Host writer permit remains global and limited to one writer; no change to its cross-recording scope is made because the current storage-provider concurrency contract and ordering policy do not establish that independent provider operations are safe to overlap. Future peer or offline-import acquisition can submit claims to this reconciliation layer; it does not need a separate archive model.

Adapters may declaratively describe historical availability as a rolling window, sequence ranges, time ranges, or `manifest` mode. Use a rolling window when the source policy is duration-based; use sequence/time ranges when the source knows exact bounds; use `manifest` when its current historical playlist is the authoritative recoverable view. The first three modes declare a bounded window or explicit coordinates and may optionally point to a historical manifest. `manifest` requires that URL and uses every eligible coordinate in the current historical media playlist as the observed recoverable set. It does not claim that absent coordinates never existed: playlist absence remains unknown and never creates a missing state. A moving window only adds newly observed coordinates; it never removes stored bytes. Explicit `EXT-X-GAP` entries retain the existing known-missing semantics. Core applies the same bounded recovery work, finite slow no-progress rechecks, and event-driven triggers to every mode. Adapters may also declare bounded request transforms for manifest, variant, media, init, or key requests: literal path-suffix replacement and selected query-parameter propagation, scoped to explicit resources and optional HTTP(S) origin allowlists. The transform never changes a target's authority, and Core still applies its own URL, redirect, and SSRF checks. For example, a source may declare a media suffix rewrite and copy one signed query value without putting platform-specific behavior in Core. Plugins do not receive an arbitrary callback to proxy or rewrite media bytes; Core performs the requests and preserves the acquired payload bytes.

The inventory and claim reconciliation primitives are independent of transport and include peer/import claim sources, so a future archive exchange can compare coordinates and verified content without changing recording semantics. Peer discovery, authentication, and P2P transport are not implemented. Legacy `recording.json` data can be adopted into the inventory as coordinate-based claims and coverage without rewriting payload objects or old archive paths; missing source-session evidence is conservatively scoped to the legacy recording. An invalid or oversized inventory is not treated as permission to mutate the canonical archive.

## Storage, privacy, and recovery

Each recording is a self-describing directory containing `recording.json`, raw manifest snapshots, payloads, and segment sidecars. The directory is the canonical source; there is no required database. A new directory is first written under a hidden incomplete name with initial metadata and then atomically published. Files are synced before rename and parent directories are synced where supported.

Segment and manifest payloads are written before their sidecars, and the sidecars before the root recording document is updated. On startup, valid sidecars can restore a segment or manifest snapshot omitted from the root document after a crash. Payload without a sidecar is preserved and reported as an orphan; corrupt or conflicting sidecars are reported without silently attaching data. An incomplete/corrupt recording is preserved and reported while other valid recordings remain loadable. Active recordings from an unclean process death become `interrupted`; pending segments become explicit gaps.

The storage facade separates logical archive keys from physical placement. A key such as `recordings/<id>/tracks/main/00000042.m4s` is validated by Core and remains independent of provider-specific bucket/object layout. Every production generation pins a provider set; the default `storage.local` provider uses the same Core-owned archive documents, sidecars, integrity checks, recovery ordering, deletion markers, and VOD projections through `ObjectStoreArchiveBackend` and `PhysicalObjectStore` as any other Storage Provider Protocol v1 implementation.

Media ingress is decoupled from durable writes: network workers read a complete, size/hash-checked response into a bounded volatile RAM ingest buffer, transfer ownership to the bounded storage queue, and return to acquisition. A single canonical writer persists from that buffer and retries storage failures without fetching the source again. Defaults are 1 GiB globally, 768 MiB per recording, 512 MiB per payload, 128 queued objects, one writer, five total persistence attempts (including the initial write) with 100 ms initial and 800 ms maximum backoff, 5-second metrics sampling, and 24-hour in-memory retention. These operational values are persisted in `management/system-settings.json` and can be edited in Settings → Storage. Storage/ingest edits are saved immediately but take effect after service restart; the existing buffer and queue are never resized under active recordings. The maximum byte limits are bounded, and the per-recording/global limits must fit the temporary old-plus-new allocation used while growing a payload. Content-Length is only a reservation hint; actual bytes remain bounded while read. **Buffered is not committed:** preview, playback, integrity, and the canonical timeline can see an object only after the complete payload is published, its sidecar is published, and `recording.json` is durably updated. This keeps canonical publication order unchanged while allowing short storage stalls to be absorbed in RAM; sustained overload applies bounded backpressure. The provider transport streams from a private disk staging object and does not duplicate the full payload in RAM.

Shutdown stops new recording admission, cancels network acquisition, then drains accepted ingest work within the caller's deadline. RAM-only bytes are volatile and are never reported as canonical. If storage remains blocked beyond the deadline, the manager returns the context error rather than waiting without bound.

Storage observability measures I/O through Integrated Recorder's storage facade, not all traffic on a physical device or cloud account. A remote provider reports capacity as unknown; Core does not present cloud storage as unlimited. By default, metrics are sampled every 5 seconds and retained in memory for 24 hours; both values are configurable within validated bounds. Retention must be at least `max(ceil(5 minutes / sampling interval) × sampling interval, 20 × sampling interval)` so the history can hold whole sample intervals for the five-minute active-observation window and the minimum 20 samples needed for each reported direction. An observed ceiling requires at least five minutes summed across actual non-idle sample intervals, plus at least 20 samples for each reported direction. Each direction remains an independent p95 estimate. The authenticated `/api/storage/pools` and `/api/storage/pools/{pool_id}/metrics` endpoints expose no absolute local filesystem path. There is one primary backend per installation; automatic placement, tiering, migration, replication, eviction, and restore are not implemented.

New archive types in `internal/domain` are separate from protocol types. Existing JSON field names are retained; epoch, ordinal, provenance, and URI classification are optional additions, so recordings without them remain readable. Adapter ID/version/protocol version/fingerprint are provenance only. Adapter state is not copied into recording metadata. A bounded private acquisition context may be retained when needed for Core-owned historical requests; it can contain signed URLs or request headers, is sensitive like source URLs and raw manifest snapshots, and is never exposed in public Recording list/detail projections. Raw session references are not used as public session identity. Recording directories therefore require restricted permissions, and public projections omit sensitive source context.

## Preview Frame Index

Scene previews are disposable projections, not source metadata or archive payloads. Recording creation accepts `preview_mode` with `disabled` or `segment`; omission means `disabled`, and a disabled recording does not start preview FFmpeg work. The policy lives outside canonical `recording.json` in management state under `<DATA_DIR>/management/previews/`. Workflow-created recordings carry the selected policy until resolution completes, then attach it to the created recording.

The Preview service periodically reconciles committed canonical recording metadata against its frame index to find missing work. It does not depend on acquisition callbacks or wait for preview results: segment scheduling, download, canonical payload writes, and metadata commits continue when the preview queue is full or FFmpeg is slow or fails. The queue is bounded and a fixed pool of two workers runs FFmpeg. An item skipped due to queue saturation is discovered on a later reconciliation. When enabled, the service generates at most one frame for each committed primary-track media segment. Init segments and manifests are not frame items.

Preview projections are stored separately at `<DATA_DIR>/previews/<recording-id>/`. Profile v1 stores clean JPEG frames bounded to 480×270. Each committed primary-track segment yields at most one reusable frame. The target-only attempt (including the required init object for fMP4) uses FFmpeg's generic keyframe filter to select the earliest decoder-reported random-access frame without codec-specific logic. If that attempt cannot produce a valid image, the extractor retries with bounded prior-segment context and ordinary decoding, seeking to the target segment boundary so dependent target pictures can be reconstructed. Fallback is limited to at most three earlier segments, 30 seconds, and 64 MiB. Context stops at source-epoch, discontinuity, or init codec-configuration boundaries. Inputs are assembled only from local copies of canonical payloads whose SHA-256 and size were checked. FFmpeg receives no remote URI; execution uses a local-only protocol allowlist and a process timeout. Unsupported or decode-failure outcomes are recorded as projection state and do not alter the recording.

`index.json` records the extraction profile and links archive ordinal, source identity, segment/frame time, source hash, image dimensions/size, and generation time. `frame_time_seconds` intentionally equals the canonical `segment_start_seconds`: the timeline is computed by summing stored preceding primary-track segment durations, and the exact decoded-frame PTS is not collected. This is an approximation, not the selected frame's measured presentation timestamp. Missing source gaps are not assigned guessed durations in the playback timeline. A frame is validated and synced before atomic publication; ready frames are not regenerated by default. After restart, valid frames are reused and only missing items are queued. Recording deletion separately cleans the preview policy and projection; safe orphan cleanup removes projections whose recording no longer exists.

Posters, the latest live preview, recording-list images, storyboards, and future seek UI all select from this same index. The default terminal poster is the ready frame nearest 25% of playback time. The default storyboard samples up to 48 unique frames uniformly across playback time, but sample count and grid columns are presentation settings rather than extraction profile. Changing sample count, poster position, or grid layout never decodes video again. The browser retains native `<video controls>` and storyboard selection seeks to the corresponding VOD playback time. `GET /api/recordings/{id}/previews` returns bounded sample/summary metadata and `/previews/{archive_ordinal}` returns one image. The existing thumbnail API remains a compatibility view of the index poster.

## Durable Watch and automatic recording

A Watch is durable management intent to record future sessions from one adapter-defined source. A Recording is one captured session and remains independent: deleting a Watch does not delete or stop its recordings, and deleting a Recording does not remove its Watch. Watch definitions/runtime live under `<DATA_DIR>/management/watches/`; input secrets use separate private files and the public API returns configured flags only. Core stores only a SHA-256 digest of adapter `session_ref`; raw session references are not returned or logged. A separate bounded/queryable projection links recording IDs to Watch/session/part metadata without changing `recording.json`.

Enabled Watches are checked by a bounded queue and fixed worker pool. Normal offline observations follow the configured interval; failures use exponential backoff and bounded jitter. Manual and scheduled checks coalesce per Watch. Errors never become offline states. A live result starts acquisition through the existing `Manager.StartResolved` path and each Watch can own at most one active Recording. While that Recording is active, Watch polling pauses. Terminal recordings wake Watch monitoring; the runtime suppresses duplicates for completed or manually stopped sessions and allows a new part after interruption. Disabling/deleting a Watch does not stop an active Recording.

Active recordings may also observe an optional adapter metadata capability independently of Watch checks. The canonical `recording.json` timeline currently stores only source `title` and `description`: Core stamps `observed_at` after validating an observation, and adapters may provide an optional `source_updated_at`. Repeated observations with the same known title/description are deduplicated; `null` means a field was not supplied, while an empty string is a known empty value. `Recording.Title` remains the compatibility/display title selected when recording starts. Metadata polling begins immediately and then uses a bounded 30-second cadence with best-effort backoff; failures do not stop media capture or create gaps. Only metadata-capable adapters are polled. The separately maintained Owncast source plugin reads `streamTitle` from `/api/status`; that endpoint does not provide a supported description or source update timestamp. Owncast is Registry-distributed rather than bundled. Chat timeline capture remains unimplemented.

## Management API and projections

`internal/recordquery` filters, searches, sorts, cursor-pages, and computes size/segment/gap statistics from canonical recording snapshots. `/api/v2/recordings` and the dashboard read those snapshots without mutating them. Gap duration is `null` when the archive lacks enough timing data. List/dashboard projections include only a small preview summary, never the full frame index, and do not make a separate status request per recording. Tags, workflow history, recording event projections, audit, notifications, and adapter enable preferences live in a separate bounded JSON store under `internal/management`; canonical recordings remain understandable without it.

Storage APIs expose the selected primary provider's bounded status, storage/ingest metrics, and a Core-generated archive index. Delete is allowed only for inactive recordings. The server's per-recording lock serializes deletion against playback and export input reads; active export/integrity jobs prevent deletion. Completed export artifacts are independent projections and remain available until their export job is deleted. Production provider-backed deletion uses Core-owned bounded object enumeration, an idempotent deletion marker, and retryable object deletes. The legacy direct-filesystem backend used by the monolithic development command retains its tombstone-based deletion helper; it is not a production Runtime Host path. The archive index lists only objects referenced by canonical metadata and never exposes absolute paths or source URIs.

Integrity verification is a bounded job service that streams canonical SHA-256/size checks against a recording metadata snapshot. Active recordings are rejected; duplicate jobs for one recording coalesce. Job/results persist separately, and queued/running work found after a process restart is marked interrupted/failed. Verification does not modify or block segment acquisition.

Resource browsing is available only to adapters declaring the generic `resource_browse` capability. Core passes list/search items, cursors, and attributes as opaque data. Queries and result pages are bounded and each call has a timeout. Adapter enable/disable preferences persist separately and are applied after each generation's immutable adapter-set discovery. Manual restart repeats the descriptor fingerprint check and cancels only workflows for that adapter; recording workers already using resolved media remain independent.

The dashboard, paginated recording query, tags, delete, archive index, events, integrity, workflow list/history, resource browse/search, global search, notifications, system-info, storage, and bounded request-log APIs use real archive or process data. `/api/logs` is an in-memory activity log containing HTTP method, status, duration, and a safe component label; it does not read OS/application log files and omits URL, query, headers, and bodies. It is cleared on process restart. Global resource search covers only resource chains already known from recordings and does not query external platforms. Notification/workflow/audit/event stores have bounded retention. Current recording event projections cover recording state, observed manifests, gaps, and management job transitions; the Core does not emit an unbounded event for every segment. Integrity verification can be canceled with `POST /api/integrity/jobs/{job_id}/cancel`.

## Authentication, settings, and derived media

Single-administrator authentication is enabled by default. First-run setup is a separate Runtime Host-owned installation lifecycle. The local `runtime-host setup-code` command prints the existing mode-`0600` one-time claim token; the browser submits it in the bootstrap form body, never in a URL or status API. A password must be 12–72 bytes and only its bcrypt hash is stored. Session tokens come from a cryptographic RNG. Only the token hash, CSRF hash, and expiry are stored as mode-`0600` per-session records under `DATA_DIR/security/sessions`; this lets overlapping Control generations share revocation and preserves a browser session across an application release activation. Browser cookies are HttpOnly and SameSite=Strict, and mutations require a CSRF header. Set `COOKIE_SECURE=1` behind a TLS reverse proxy. `AUTH_DISABLED=1` is accepted only for loopback binds. There is no user/role system, password reset, or external identity provider.

Installation identity and readiness are shared across application generations and stored at `DATA_DIR/runtime/installation.json`, separate from the canonical recording archive and product-management records. Runtime Host validates this bounded mode-`0600` state and owns its transitions:

```text
uninitialized → setup_in_progress → ready
       └──────────────→ ready (loopback-only AUTH_DISABLED)
any invalid/corrupt critical state → recovery_required
```

If the installation record is absent but a valid administrator already exists, Host atomically migrates the legacy install to `ready`; if a `ready` install loses its administrator, it fails closed to `recovery_required`. Before `ready`, Control serves only setup/authentication and allowlisted read-only diagnostics. Watch scheduling, retention, preview reconciliation, and storage metrics producers stay stopped; ordinary product mutations and update activation are rejected. Setup completion asks the active Control over lifecycle IPC to validate storage readiness, commits `ready` durably in Host, then sends an idempotent activation signal. A Host/Control restart reconciles producer activation from the durable state, so no restart is required after the wizard finishes and setup state is never generation-local.

The Runtime Host intercepts `GET /api/runtime/update` and authenticated, CSRF-protected `POST` operations at `/check`, `/stage`, `/activate`, and `/rollback`. Update status is a bounded public projection and omits paths, PIDs, tokens, and raw release notes; it may include a bounded, plain-text release-notes summary rendered as text. Development builds fail closed for remote updates. A release activation replaces the default application generation while active Recordings stay pinned to their current Engine. The Runtime Host/container itself is not self-updated by this API.

`internal/systemsettings` manages the UI theme (immediate), integrity concurrency (persisted but applied after server restart), storage/ingest operating limits (persisted and applied after restart), and an optional retention policy. The Storage settings API reports both saved values and the effective startup snapshot, plus fields that require restart. Writer concurrency currently accepts only one writer to preserve canonical commit ordering. Retention defaults to disabled with a 30-day age threshold. When enabled, only completed recordings older than the configured threshold are eligible; any tagged recording is protected, as are recordings with active integrity or derivative jobs. The server performs one bounded pass at startup and then every 24 hours, deleting at most 100 recordings per pass. `GET /api/retention/candidates` previews candidates and `POST /api/retention/run` explicitly runs a pass. Bind address, storage root, and adapter directories are read-only. Settings use strict validation and atomic private-file replacement.

`internal/preview` and optional `internal/derivative` services run only after canonical media commits. Host installations work normally for acquisition, canonical archival, and VOD without FFmpeg; only preview generation and MKV `-c copy` export are unavailable. Export validates and privately copies source HLS payloads into a separate staging directory, creates a local playlist, and uses a structured argument vector without a shell or network protocols. Preview and export staging/jobs live outside the canonical archive and use cancellation, process timeouts, and bounded concurrency. Preview extraction follows the Preview Frame Index contract above and does not replace existing ready frames. There is no independent single-thumbnail decode pipeline; the existing thumbnail read/regenerate compatibility API operates through the Preview Frame Index. FFmpeg and JPEG failures do not change the archive. Transcoding and additional export containers are not implemented.

Recording directories are mode `0700`; metadata, payload, and sidecar files use mode `0600`. File secret/state backends do not encrypt values at rest. The management API provides one administrator but no multi-user/role authorization. Local runs bind to loopback by default and Compose publishes only on `127.0.0.1`. Use TLS and Secure cookies behind a reverse proxy, and do not expose the control plane directly to untrusted networks. The page bundles hls.js 1.6.7 (Apache-2.0) and retains restrictive CSP/security headers. Scripts remain same-origin only; `style-src-attr` narrowly permits the inline style attributes Radix needs to position popovers and selects.

## Server lifecycle and Docker

On SIGINT/SIGTERM, the Runtime Host stops the stable listener and supervises bounded shutdown of its child processes. On a normal Host/container stop, the Control fences new management work and stops its Watch scheduler; each Recorder Engine then drains its accepted ingest queue and closes its own recording workers and adapter processes. Application release activation does not stop Engines. A Host/container replacement is maintenance: active recordings can be recovered as interrupted if their Engine cannot finish its bounded shutdown or if it crashes. Enabled Watches are reconciled and staggered after cold startup.

The container runs as UID 10001. Compose uses a named `/data` volume and publishes the Runtime Host listener on host loopback. The image contains the Runtime Host, an immutable initial Control/Engine release, the Host-declared bundled HLS executable at `/adapters/integrated-recorder-adapter-hls`, and the standalone `storage.local` executable. It does not bundle Owncast. Existing `/data/recordings`, `/data/management`, and `/data/security` remain in place; `/data/recordings` is the Host-controlled archive root passed only to `storage.local`, while generation registry, owners, runtime credentials, installed releases, imported adapter/storage artifacts and sets, Plugin Registry desired state, and recovery coordination remain Core-owned under `/data/runtime`. This adopts legacy recordings without moving their files. The Host does not grant `storage.local` the `/data` root. The image also includes the `ffmpeg` package from Alpine v3.21's community repository. Alpine package metadata lists the ffmpeg license expression as `GPL-2.0-or-later AND LGPL-2.1-or-later`; FFmpeg upstream documents how GPL-enabled optional components affect FFmpeg licensing. This is a package metadata notice, not legal advice or a statement changing Integrated Recorder's own license. Check the exact package/build included in an image before redistribution. References: [Alpine v3.21 ffmpeg package metadata](https://pkgs.alpinelinux.org/package/v3.21/community/x86/ffmpeg), [FFmpeg legal considerations](https://ffmpeg.org/legal.html). Mount additional operator-supplied executable adapters read-only at `./adapter-binaries` (container path `/external-adapters`); set `IR_ALLOW_OPERATOR_PLUGINS=1` to enable their import. Runtime Host validates and imports them into immutable sets without a Host/container restart. They are labeled Local / Operator trusted and Not reviewed by Integrated Recorder. Registry source/storage plugins are managed from `/adapters`; `storage.local` remains bundled and mandatory. Even when authentication is explicitly disabled, only loopback binds are allowed.

## Playback and intentionally unimplemented work

For a stopped, completed, or interrupted recording, Core creates a finite seekable HLS VOD manifest over stored source segments. Segment endpoints return stored bytes directly; playback does not concatenate or remux files. Browser codec support remains necessary.

Not implemented: chat timeline, asynchronous adapter notification runtime, real platform authentication flows, additional bundled platform-specific source adapters, workflow persistence across Core restart, encrypted HLS, external rendition synchronization, DASH, archive finalization/TAR, LTO, export transcoding/additional formats, multi-user/role authorization, adapter sandboxing, publisher PKI/signing, community registry hosting, automatic plugin updates, and plugin dependency resolution. Watch checks are polling-based; webhook/push notifications are not implemented.

## Web application

The management UI is a React 19 + TypeScript SPA under `web/`. It uses Vite, Tailwind, shadcn-style Radix UI components, TanStack Query/Router/Table, Lucide, and hls.js. API requests and CSRF handling live in a shared client; TanStack Query owns server state. The browser uses same-origin `/api` endpoints, and the player bundles hls.js locally.

For the legacy monolithic local development command, run the Go API and Vite in separate terminals. This path is useful for iterating on API/UI behavior but does not provide Runtime Host generation updates or cross-process global resource coordination:

```sh
go run ./cmd/archiver
npm --prefix web ci
npm --prefix web run dev
```

Production Go binaries embed Vite output under `internal/server/static/ui/`. `make build` builds the frontend before Go; the Dockerfile uses a separate Node build stage. Only allowlisted client routes receive the SPA entry on direct navigation. `/api/**` and `/static/**` are excluded from SPA fallback.

On first start, the UI checks the Runtime Host's public `/api/setup/status` before authentication. An incomplete installation opens `/setup`; a ready installation then checks `/api/auth/session` and opens `/login` when necessary. The administrator claim reuses `/api/auth/bootstrap`, after which the authenticated browser begins and completes the Host-owned setup transaction. Setup code is never placed in a URL or returned by an API. After login, the shared API client automatically sends the session CSRF token on mutation requests.
